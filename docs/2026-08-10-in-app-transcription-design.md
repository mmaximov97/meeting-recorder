# Транскрипция в приложении — дизайн

**Дата:** 2026-08-10
**Статус:** утверждён, готов к плану реализации
**Контекст:** независим от `docs/2026-08-10-macos-port-design.md` — платформенно-нейтрален, кода из того трека не требует и не блокируется им.

## Зачем

Сегодня транскрипция в meeting-recorder не встроена вообще: она делается вручную скиллом Claude Code `ailab-transcribe` после записи, а URL шлюза и ключ у него зашиты в `~/.claude/skills/ailab-transcribe/scripts/transcribe.sh` (`GATEWAY="${AILAB_GATEWAY:-http://10.0.0.3:8080}"`, ключ — дефолтный литерал в самом скрипте). Это работает только там, где есть Claude Code и доступ именно к этому ai-lab. Нужно, чтобы приложение умело транскрибировать сами, с шлюзом и ключом, которые пользователь указывает в настройках — не тем самым скриптом и не зашитыми путями к конкретному серверу.

## Что НЕ входит

- **Модель/язык в UI.** Дефолты (`Systran/faster-whisper-large-v3`, `ru`) захардкожены — ровно то же, что скрипт использует по умолчанию сегодня. Выносить в настройки, если понадобится другой язык/модель, — отдельная, более поздняя доработка.
- **Диаризация внутри дорожки собеседников по именам.** `SPEAKER_00`/`SPEAKER_01` от шлюза схлопываются в одну метку «Собеседники» — различать конкретных людей в общей дорожке не входит в этот дизайн.
- **Отмена запущенной транскрипции.** Задача идёт до конца или до ошибки; кнопки «Отменить» нет.
- **Параллельная транскрипция нескольких записей.** Одновременно — только одна; вторая попытка получает понятную ошибку, а не встаёт в очередь.
- **Просмотр транскрипта внутри приложения.** Результат открывается тем же способом, что и сейчас — через «Открыть папку».
- **Изменения в скилле `ailab-transcribe`.** Он остаётся для случаев вне приложения (произвольные аудио/видео вне `~/Recordings`); эта работа его не трогает и не заменяет.
- **macOS-специфика.** Вся эта фича — чистый HTTP + файловый ввод-вывод, `cfg`-развилок не требует и одинаково работает на обеих ОС.

## Решения и обоснования

### Настройки: расширение существующего `Config`

```rust
// src-tauri/src/config.rs
#[derive(Serialize, Deserialize, Default, Clone, PartialEq, Eq, Debug)]
#[serde(default)]
pub struct Config {
    pub mic_device_id: Option<String>,
    pub mic_device_name: Option<String>,
    /// Базовый URL шлюза, например `http://10.0.0.3:8080` или
    /// `https://ai-lab.cypher-cloud.net`. Без хвоста `/v1/...` — его
    /// дописывает клиент транскрипции.
    pub stt_gateway_url: Option<String>,
    pub stt_api_key: Option<String>,
}
```

Тот же файл (`app_config_dir()/config.json`), тот же формат, тот же принцип «битый конфиг — это `Config::default()`, а не паника» — тут ничего нового не изобретается, только два новых поля. `#[serde(default)]` уже стоит на структуре, так что старый `config.json` без этих полей читается как есть (оба `None`); `PartialEq, Eq` остаются выводимыми как и раньше — оба новых поля `Option<String>`, `Eq` тут ничего не ломает (в отличие от `Recording::imbalance_db: Option<f32>` в другом месте кода, где `Eq` как раз убран). Ключ хранится тем же способом, что и `mic_device_id` сегодня — тот же уровень защиты: файл лежит в папке профиля пользователя ОС, шифрования нет.

Хранить ключ иначе (Keychain/Credential Manager) сознательно не стали: личная машина одного пользователя, новая зависимость и код ради одного поля не оправданы, а у ключа `ailab` и так узкий scope (`stt` на один проект) — цена компромисса невысокая.

### Контракт шлюза (уже подтверждён работающим скриптом, не изобретается заново)

```
POST {gateway}/v1/audio/transcriptions/async
  Authorization: Bearer {key}
  multipart/form-data: file=<wav>, language=ru, model=Systran/faster-whisper-large-v3, diarize=true
  → 202 { "id": "..." }

GET {gateway}/v1/jobs/{id}
  Authorization: Bearer {key}
  → { "status": "queued"|"processing"|"succeeded"|"failed"|"error"|"cancelled",
      "result": {
        "text": "...",                                    // всегда, если succeeded
        "segments": [{ "start": 12.3, "speaker": "SPEAKER_00", "text": "..." }],  // только если диаризация прошла
        "diarization_skipped": true                        // только если её не хватило на GPU
      },
      "error": "..." }                                     // только если failed/error
```

Опрос — раз в 10 секунд, до 360 попыток (~60 минут) — тот же лимит, что уже проверен в `transcribe.sh`.

### Пайплайн: два job'а параллельно, слияние по времени

Новый модуль `src-tauri/src/transcribe.rs`:

```rust
pub struct TrackResult {
    pub segments: Vec<Segment>,   // пусто, если диаризация не уместилась
    pub text: String,             // сплошной текст — фолбэк, если segments пуст
}

pub struct Segment {
    pub start: f64,
    pub label: Label,             // Owner | Others — не SPEAKER_00/01, см. ниже
    pub text: String,
}

pub enum Label { Owner, Others }

pub async fn submit_and_poll(
    client: &reqwest::Client,
    gateway: &str,
    key: &str,
    wav_path: &Path,
    label: Label,
) -> Result<TrackResult, TranscribeError>;

pub fn merge(mic: TrackResult, system: TrackResult) -> String;   // готовый .md
```

`submit_and_poll` зовётся дважды параллельно (`tokio::try_join!` — обе задачи `Send`, в отличие от аудио-потока, здесь никакого `!Send` нет, поэтому лишний поток и каналы не нужны, обычный `async fn` под `#[tauri::command] async fn` и встроенный рантайм Tauri справляются без своей инфраструктуры). Каждый вызов помечает свои сегменты `Label::Owner`/`Label::Others` — не «SPEAKER_00/01» от шлюза: это и есть та самая схлопка отдельных голосов собеседников в одну метку, которую этот дизайн сознательно выбирает.

`merge` сортирует объединённый список сегментов по `start` и выводит `.md` построчно (`**[MM:SS]** _Владелец/Собеседники_ текст`), тем же визуальным форматом, что уже пишет `transcribe.sh`. Если у одной из дорожек `segments` пуст (диаризация не уместилась на GPU — `diarization_skipped`), эта дорожка идёт отдельным блоком в конце файла с пометкой `(без привязки ко времени — диаризация не уместилась)`, а не пытается влезть в хронологию, которой для неё не существует. `.txt` собирается из того же объединённого порядка, без меток времени и без speaker-меток — plain-текст для тех же целей, что и сегодня.

### Частичный отказ — пишем то, что получилось

Если весь `submit_and_poll` одной из дорожек упал (сеть, 4xx/5xx, таймаут) — вторая дорожка всё равно доводится до конца, и `.transcript` пишется с одной дорожкой плюс явной пометкой, какая не удалась и почему. Полный отказ (нечего писать) — только если упали ОБЕ. Это тот же принцип, что уже применяется в `close_sinks`/`open_sinks` (частичный успех дешевле полного отказа) — новый код здесь просто следует существующей конвенции проекта, а не изобретает свою.

### Куда пишется результат

`{dir}/{base}.transcript/{base}.md` и `.txt` — ровно та же папка и то же имя, которые уже понимает `rename.rs` (`SUFFIXES` включает `.transcript`, переименование двигает её вместе с дорожками). Никакой новой файловой конвенции: этот код просто становится вторым производителем той же структуры, которую раньше писал только `transcribe.sh`.

### Одна транскрипция за раз

```rust
// src-tauri/src/main.rs — новое состояние Tauri
struct Transcribing(Mutex<Option<String>>);   // Some(base) — что сейчас транскрибируется
```

`#[tauri::command] async fn transcribe_recording(...)` в начале пытается атомарно поставить `Some(base)`, если там уже `None`; если уже что-то идёт — сразу возвращает `Err("уже идёт транскрипция другой записи")`, не запуская второй пайплайн. По завершении (успех или ошибка) — сбрасывает обратно в `None`. Тот же стиль, что `Cmd`/`Status`/`Cache` уже используют для состояния, разделяемого между командами.

### Прогресс и ошибки — событиями, как уже устроено для записи

```rust
app.emit("transcribe-progress", json!({ "folder": ..., "base": ..., "stage": "uploading" | "polling" | "merging" }));
app.emit("transcribe-done", json!({ "folder": ..., "base": ... }));
app.emit("transcribe-error", json!({ "folder": ..., "base": ..., "message": ... }));
```

Тот же паттерн, что `audio.rs` уже применяет для `state`/`levels`/`error` — фронтенд слушает события, а не поллит. `folder`+`base` в пейлоаде — чтобы список записей понимал, какая именно строка обновилась (записей может быть много, событие должно быть адресным).

### UI

Блок настроек — компактная секция в существующем окне (не отдельное окно): поле URL шлюза, поле ключа (`type="password"`), сохранение по потере фокуса (blur), тем же вызовом `invoke`, что уже есть у `set_mic_device`. Кнопка **«Транскрибировать»** — в строке записи, показывается только когда `rec.mic && rec.system` (это поле уже вычисляется на сервере, во фронтенд ничего нового не течёт). Во время выполнения кнопка неактивна и показывает стадию из `transcribe-progress`; по `transcribe-done` — короткое «Готово», по `transcribe-error` — текст ошибки на месте кнопки. Кнопка не проверяет, есть ли уже `.transcript` — повторный клик просто перезаписывает результат; открыть существующий транскрипт — по-прежнему через «Открыть папку».

### Новая зависимость

`reqwest` (с фичами `json`, `multipart`) добавляется в `src-tauri/Cargo.toml` — HTTP-клиента в проекте сегодня нет вообще, `tauri`/`serde_json` для отправки multipart-файла недостаточно.

## Отказы

| Отказ | Поведение |
|---|---|
| URL/ключ не заданы | Кнопка «Транскрибировать» ведёт себя как обычно, команда сразу отдаёт понятную ошибку («настройте URL и ключ шлюза») |
| Сеть недоступна / шлюз не отвечает | Ошибка конкретной дорожки, вторая дорожка (если успела) — не теряется |
| Ключ неверный (401/403) | Ошибка сразу, без 360 попыток поллинга — не тот случай, где имеет смысл ждать |
| Диаризация не уместилась на GPU у одной дорожки | Эта дорожка идёt отдельным блоком без таймкодов, вторая — с ними как обычно |
| Обе дорожки упали | `.transcript` не создаётся, явная ошибка в UI |
| Повторный клик по уже идущей транскрипции (той же или другой записи) | Мгновенная ошибка «уже идёт другая транскрипция», второй пайплайн не стартует |

## Тесты

- `merge` — чистая функция, тестируется без сети: сортировка вперемешку заданных сегментов по `start`, схлопка `SPEAKER_00`/`01` в единый `Others`, деградация одной дорожки без `segments` в хвостовой блок, обе дорожки без `segments` (полный текстовый фолбэк).
- Разбор ответа `GET /jobs/:id` — чистая функция над JSON-фикстурами: `succeeded` с сегментами, `succeeded` с `diarization_skipped`, `failed`/`error` с сообщением.
- HTTP-клиент (`submit_and_poll`) — не юнит-тестируется без реального шлюза, аналогично тому, как `WindowsDetector`/`capture` не тестируются без железа; проверяется вручную на реальном ai-lab.
- Guard «одна транскрипция за раз» — тестируется на моке состояния без реального пайплайна.

## Порядок работ

1. `Config` + команды чтения/записи настроек + блок UI — самодостаточно, проверяется без единого HTTP-запроса.
2. HTTP-клиент шлюза (submit + poll одной дорожки) — новая зависимость, ручная проверка на реальном ai-lab.
3. `merge` как чистая функция + её тесты — независимо от HTTP-клиента.
4. Оркестрация двух дорожек параллельно, guard «одна за раз», события прогресса.
5. Кнопка и статусы в UI записи.

Первый пункт самодостаточен и не требует остальных — настройки можно проверить, даже если транскрипция ещё не подключена.
