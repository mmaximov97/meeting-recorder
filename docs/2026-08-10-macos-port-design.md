# Порт на macOS — дизайн

**Дата:** 2026-08-10
**Статус:** утверждён, готов к плану реализации
**Контекст:** README уже называет macOS «точкой расширения» через трейты `MeetingDetector` и (по факту) границу `AudioIo` — этот документ впервые доводит расширение до конкретной архитектуры.

## Зачем

Приложение сейчас работает только на Windows: система детекта звонка — WASAPI audio sessions, системный звук — WASAPI loopback поверх `cpal`, оба варианта у macOS не существуют в том же виде. Нужно писать встречи (микрофон + системный звук отдельными дорожками) с того же macOS-инстанса Tauri-оболочки, с тем же UX (трей, хоткей, тост-предложение, список записей, выбор микрофона), без деградации до «только микрофон».

Целевая машина — **macOS 14.4+**. Это не случайный выбор минимальной версии: именно с 14.2 в Core Audio появился публичный **Process Tap API** (`AudioHardwareCreateProcessTap`), который снимает системный звук напрямую, без виртуального аудио-драйвера и без изменения звукового вывода пользователя. На более старых macOS пришлось бы либо ставить `BlackHole` и вручную (или скриптом) собирать Multi-Output Device, либо использовать `ScreenCaptureKit` с разрешением «Запись экрана» — оба варианта явно отклонены как избыточное трение для личного инструмента, когда версия ОС это трение снимает.

## Что НЕ входит

- **Настройка URL/ключа транскрибатора.** Отдельная задача, платформенно-независимая (актуальна и для Windows) — отдельный дизайн-документ после этого порта.
- **Поддержка macOS < 14.2.** Process Tap API недоступен — приложение на старте явно откажется запускаться с понятным сообщением, а не будет тихо деградировать до «только микрофон» или тянуть второй, more сложный путь через `ScreenCaptureKit`/`BlackHole`.
- **Нотаризация и Developer ID.** Личный инструмент на собственной машине, распространять его не нужно. Но см. ниже: ad-hoc подпись (бесплатная, без аккаунта разработчика) — не «нотаризация» — обязательна, иначе часть функциональности не заработает вообще.
- **Sandboxing.** `com.apple.security.app-sandbox` выключен — Process Tap под сэндбоксом работает нестабильно (задокументированный источниками риск), а дистрибуции через App Store не планируется.
- **Свой звуковой выход / раздельный выбор устройства для системной дорожки.** Тот же принцип, что уже зафиксирован в спеке про выбор микрофона: системный звук снимается с того же микса, который слышит пользователь.

## Решения и обоснования

### Границы: платформенный код живёт за уже существующими трейтами

`AudioIo` (`src/app.rs`) и `MeetingDetector` (`src/detector/mod.rs`) — это ровно та граница, за которой должна спрятаться macOS-реализация. `App`, машина состояний, `storage`/`rename`/`imbalance` не знают и не должны узнать, какая ОС под ними — это уже проверено тем, что они тестируются на подставных `AudioIo`/`SinkFactory` без единого вызова в железо.

Меняются только:

```
src/capture/mod.rs      — общий код (Resampler, downmix, форматы) остаётся общим
src/capture/windows.rs  — НОВЫЙ: build_loopback_capture + start_silence переезжают сюда
src/capture/macos.rs    — НОВЫЙ: системная дорожка через Process Tap
src/detector/windows.rs — без изменений
src/detector/macos.rs   — НОВЫЙ: детект по процессам + активности
```

`build_mic_capture` остаётся в `capture/mod.rs` без изменений и без `cfg` — `cpal` уже умеет вход CoreAudio так же, как WASAPI, микрофонная дорожка платформы не касается вообще.

Разнесение `build_loopback_capture`/`start_silence` в `capture/windows.rs` — не обязательный рефакторинг, а следствие того, что `detector/` уже показывает правильную форму (общий `mod.rs` + файл на платформу): делать иначе для `capture/` значило бы завести два разных способа организации платформенного кода в одном крейте.

`Cargo.toml` (корневой пакет) получает target-specific секции:

```toml
[target.'cfg(windows)'.dependencies]
windows = { version = "0.58", features = [...] }   # то, что сейчас в [dependencies.windows]

[target.'cfg(target_os = "macos")'.dependencies]
objc2-core-audio = "..."          # CATapDescription; покрытие остальных функций — см. план, Задача 3
objc2-core-foundation = "..."     # транзитивная зависимость objc2-core-audio
```

`sysinfo` остаётся безусловной зависимостью — он уже кросс-платформенный и нужен на обеих ОС (Windows: имя процесса по pid; macOS: список известных звонилок).

### Системный звук: Core Audio Process Tap

Новый модуль `capture/macos.rs` открывает process tap на системный микс (а не на конкретный процесс — узнать заранее, какой процесс окажется звонилкой, мы не можем, да и это не нужно: интересен весь микс, ровно как сейчас на Windows). Форма наружу — та же, что у `build_loopback_capture`: конструктор, отдающий `PendingCapture`-подобный объект и льющий `Vec<i16>` в тот же `Sender`, которым сегодня пользуется `CpalAudio::open()`. Так `src-tauri/src/audio.rs` и `App` не видят разницы между платформами — там просто появится `#[cfg(target_os = "windows")]`/`#[cfg(target_os = "macos")]` при выборе, какую функцию открытия системной дорожки звать.

`start_silence()` (трюк с тихим render-потоком, будящий спящий WASAPI loopback-эндпоинт) на macOS не нужен вообще: Process Tap отдаёт микс независимо от того, «простаивает» ли устройство вывода в терминах WASAPI — на CoreAudio такого понятия нет. `CpalAudio::open()` в `src-tauri/src/audio.rs` зовёт `start_silence()` только под `#[cfg(target_os = "windows")]`.

Формат сэмплов, который отдаёт Process Tap (частота дискретизации, число каналов, `f32`/`i16`), заранее не фиксирую — ресемплер и даунмикс в `capture/mod.rs` уже написаны обобщённо ровно под эту неопределённость (`downmix_to_mono_f32`/`Resampler`), новый код их переиспользует, а не дублирует.

**Разрешение системы.** Первое обращение к Process Tap показывает системный диалог (аналог того, что сейчас происходит с микрофоном) — пользователь один раз разрешает, macOS запоминает. Отказ пользователя не должен ронять приложение: дорожка `system` в этом случае останется пустой (44 байта, только заголовок) — ровно то же поведение, что сегодня даёт полная тишина в системе на Windows, и уже покрыто существующей пометкой дисбаланса громкости.

**Rust-биндинг.** Зрелых safe-обёрток нет, но сама последовательность вызовов задокументирована независимыми источниками (гайды 2026 года, открытый инструмент AudioTee, Swift-пример insidegui/AudioCap) и звучит одинаково у всех: `CATapDescription` (тап на весь микс, не на конкретный процесс) → `AudioHardwareCreateProcessTap` (здесь всплывает TCC-диалог) → словарь агрегированного устройства, где **реальное** устройство вывода — главный саб-девайс, а тап подключён отдельным `kAudioAggregateDeviceTapListKey` (тап главным саб-девайсом даёт тишину — это задокументированная ловушка) → `AudioHardwareCreateAggregateDevice` → чтение сэмплов через `AudioDeviceCreateIOProcIDWithBlock` на агрегированном устройстве (`AVAudioEngine` сюда не ретаргетится — молча продолжает читать дефолтный вход, это тоже задокументированная ловушка). Крейт `objc2-core-audio` уже экспонирует `CATapDescription`; экспонирует ли он сами функции `AudioHardwareCreateProcessTap`/`AudioHardwareCreateAggregateDevice`/`AudioDeviceCreateIOProcIDWithBlock` — первое, что проверяется в спайке (план, Задача 3); если нет — пишутся вручную как `extern "C"` над `CoreAudio.framework`, в духе того, как `detector/windows.rs` уже оборачивает COM-вызовы `IAudioSessionManager2`.

### Детект начала звонка: процессы + активность звука

`detector/macos.rs` реализует `MeetingDetector` без единого прямого аналога WASAPI audio sessions — вместо «кто держит микрофон» используется двухсигнальная эвристика:

1. **Известный процесс.** `sysinfo` (уже в зависимостях) ищет по списку известных звонилок (`zoom.us`, `Microsoft Teams`, `Slack`, браузеры — с оговоркой, что вкладку конкретного сайта типа Google Meet изнутри Chrome не отличить, см. «Отказы»).
2. **Активность звука.** Тот же Process Tap, что открыт для системной дорожки записи (см. выше), проверяется на не-тишину за короткое скользящее окно — так тост «Записать?» не всплывает на голом факте «Zoom открыт», если звонок ещё не начался или уже закончился, а окно просто не закрыли.

Оба условия обязаны совпасть, чтобы `MeetingDetector::poll()` вернул сессию. Это осознанно не то же самое сравнение, что на Windows: неизвестная звонилка (не в списке процессов) не задетектится вообще — деградация ровно до «пользуйся хоткеем/кнопкой», которые работают независимо.

**Важно про privacy-инвариант.** Сигнал «активность звука» берётся из **системного** тапа (то, что играет наружу), а не из микрофона. Микрофон в этом коде открывается по-прежнему только на `Action::StartRingBuffer` (детект подтверждён) или явную проверку — открывать его ради самого детекта значило бы нарушить документированный в `app.rs` инвариант «индикатор микрофона горит ровно тогда, когда мы слушаем». Системный тап под этот инвариант не подпадает: он не про запись со стороны пользователя, индикатора микрофона не касается.

### Хранилище записей и открытие папки

```rust
// src-tauri/src/main.rs
#[cfg(target_os = "windows")]
fn recordings_root() -> PathBuf { PathBuf::from(r"C:\Users\Cypher\Recordings") }

#[cfg(target_os = "macos")]
fn recordings_root() -> PathBuf {
    dirs::home_dir().expect("$HOME обязан существовать").join("Recordings")
}
```

`~/Recordings`, а не `~/Documents/Recordings` — та же причина, по которой они и сейчас лежат вне vault: `~/Documents` на macOS по умолчанию попадает под синк iCloud Drive «Рабочий стол и Документы», а ~150 МБ на встречу туда попадать не должны ровно по тем же основаниям, что и в git-синкаемый vault (см. README, раздел «Важно»).

`open_folder()` переключается с `explorer.exe` на `open`:

```rust
#[cfg(target_os = "macos")]
std::process::Command::new("open").arg(&dir).spawn()...
```

Код возврата не проверяется по той же причине, что и сейчас с `explorer.exe`.

### Упаковка Tauri

- `tauri.conf.json`: `bundle.targets` для macOS — `["app", "dmg"]` вместо `["nsis"]`. Tauri поддерживает разный набор таргетов per-platform в одном конфиге.
- Иконка: нужен `.icns` рядом с существующими `.ico`/`.png`.
- `Info.plist`: `NSMicrophoneUsageDescription` — для диалога разрешения на микрофон. `NSAudioCaptureUsageDescription` — отдельный, для Process Tap; это **другая категория TCC**, не переиспользует микрофонный диалог.
- **Ad-hoc подпись сборки — не опционально.** По независимым источникам (гайд по Core Audio Tap API 2026 года, инструмент AudioTee), `AudioHardwareCreateProcessTap` на неподписанном бинарнике не показывает системный диалог разрешения вообще — то есть без подписи фича молча не работает, а не работает с деградацией. Ad-hoc подпись бесплатна и не требует аккаунта разработчика (`codesign --sign - MyApp.app` или соответствующая опция бандлера Tauri); полноценная нотаризация не нужна, но пустая/нулевая подпись — не вариант. Это добавляет шаг в сборку, которого не было на Windows.
- Трей (`tray-icon`), тост (`tauri-plugin-notification`), глобальный хоткей (`tauri-plugin-global-shortcut`), скрытие окна по крестику — все уже кросс-платформенные Tauri-плагины, ожидаются рабочими без переписывания логики; проверить на месте.
- Хоткей остаётся **Ctrl+Shift+R** (не Cmd+Shift+R) — та же комбинация на обеих машинах, чтобы не ломать моторную память.
- Сборка — нативным `cargo`/`tauri` прямо на маке. Раздел README «Сборка (из WSL)» получает отдельный, гораздо более простой macOS-вариант без interop-обвязки (`cargo.exe` через WSL — Windows-специфичная деталь, на маке её просто нет).

### Что не меняется

`Config::load`/`save` (уже кросс-платформенный `app.path().app_config_dir()`), вся машина состояний (`session.rs`), `storage.rs`, `rename.rs`, `imbalance.rs`, `ringbuf.rs` — ни один не содержит платформенного кода и не должен его получить.

## Отказы

| Отказ | Поведение |
|---|---|
| macOS < 14.2 (Process Tap недоступен) | Приложение не запускается, явное сообщение о минимальной версии — не тихая деградация |
| Пользователь отказал в разрешении на Process Tap | Дорожка `system` пустая (как при полной тишине сегодня), запись не падает |
| Известная звонилка запущена, но звука ещё нет | Тост не показывается — это ожидаемое поведение, не отказ |
| Звонилка не входит в список известных процессов | Авто-детект не срабатывает, ручной старт (кнопка/хоткей) работает как обычно |
| Process Tap отвалился на середине записи (устройство/маршрут звука сменился) | Дорожка `system` обрывается, `mic` дописывается до конца — тот же принцип частичного успеха, что уже есть в `close_sinks` |

## Тесты

Без реального железа и без Process Tap, тем же принципом, что уже применён к `WindowsDetector` (сам он не покрыт юнит-тестами — покрыты только чистые функции вокруг него):

- Список известных процессов звонилок — чистая функция `is_known_meeting_process(name: &str) -> bool`, тестируется без sysinfo.
- Решение «есть активность звука» по буферу сэмплов — чистая функция над `&[i16]`/`&[f32]` с порогом, тот же стиль, что уже есть у `peak()` в `app.rs`.
- Комбинация двух сигналов в решение «звонок идёт» — чистая функция, аналог `poll_to_event`, тестируется без реального детектора.
- Сам FFI-слой Process Tap — как и `WindowsDetector::poll()`, не юнит-тестируется; проверяется вручную на реальной машине.

## Порядок работ

От самого рискованного (чтобы риск проявился рано) к обвязке:

1. **Реструктуризация `capture/`** — вынести Windows-код в `capture/windows.rs`, завести `target.'cfg(...)'.dependencies` в `Cargo.toml`. Чисто механическая правка, Windows-сборка остаётся зелёной на каждом шаге.
2. **Process Tap FFI** для системной дорожки — самая большая неизвестность, делается первой среди нового кода.
3. **Детект на macOS** (`sysinfo` + активность звука из тапа) — переиспользует тап из п. 2.
4. **`recordings_root()`/`open_folder()`** под `cfg(target_os = "macos")`.
5. **Упаковка**: иконки, `Info.plist`, bundle targets, проверка трея/хоткея/тостов на реальной машине.
6. **Guard на версию macOS** и явные сообщения об отказе разрешения.

Пункт 1 самодостаточен и не рискует ничем на Windows. Пункты 2–3 — тот кусок, который стоит подтвердить на реальном железе раньше, чем вкладываться в упаковку и полировку.
